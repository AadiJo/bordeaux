Trajectory Optimizer Strategy for Bordeaux

Projectbordeaux
Versionv1
Statusactive · 2026-08-09

Replace Bordeaux's current “optimized” smoothing pass with a deterministic, fixed-path, time-optimal parameterizer inspired by TOPP-RA; keep full nonlinear geometry optimization as an explicit later tool, not the default planner.

Verdict. Choreo's TrajoptLib + Sleipnir is the best complete open-source FRC trajectory optimizer, but a custom reachability parameterizer is the best product fit for Bordeaux. It preserves the path the user drew, solves in roughly linear time, and can distinguish invalid inputs from numerical failures instead of collapsing both into “unsolvable.”

Executive findings

  • Sleipnir is not inherently a bad solver. It is a sparse reverse-mode autodiff and interior-point NLP system. Choreo gives it a difficult, nonconvex, free-time direct-collocation problem with roughly 19 decision variables per swerve sample: pose representation, translational/angular velocity and acceleration, eight module-force components, and timestep. At Choreo's default 50 ms target interval, a normal autonomous path quickly becomes a problem with thousands of variables and constraints.
  • “Unsolvable” often means solver failure, not physical impossibility. Current Sleipnir exposes distinct statuses for local/global infeasibility, factorization failure, line-search failure, feasibility-restoration failure, nonfinite guesses, divergence, iteration limit, and timeout. Choreo currently treats every negative status as generation failure. Choreo 2026.0.3 explicitly added a fallback for line-search failure and warns that the fallback may still end in feasibility-restoration failure.
  • Bordeaux already owns the geometry. Its Bezier/line/arc/clothoid geometry, authored stops, heading laws, constraint ranges, rotation-priority behavior, stationary actions, migrations, and Java format are product invariants. A planner that silently moves that geometry is a mismatch.
  • Bordeaux's existing “optimized” planner is not a nonlinear optimizer. src/shared/planners/optimizedTrajectory.ts starts with profiledSpline, smooths its velocity samples, reprojects acceleration/deceleration envelopes, and remaps timestamps. It does not alter geometry or solve a global optimum.
  • The existing implementation is already computationally cheap, but not faster in trajectory time. An informal local baseline (30 warm runs, 57–1,345 samples) put the current optimized planner around 0.2–8.4 ms p95, yet its smoothed trajectories were 7–65% longer than profiledSpline in the synthetic cases. This is a baseline observation, not a production benchmark.

What Choreo actually solves

Choreo's swerve generator minimizes the sum of variable timesteps while enforcing discrete kinematics, pose/waypoint constraints, per-module velocity and force norms, net-force dynamics, and net-torque dynamics. That formulation can find a different geometric path between waypoints and makes unusually complete use of the drivetrain. It is also nonconvex because heading is represented with sine/cosine, dynamics multiply state by variable timestep, and obstacle/region constraints reshape the feasible set.

Sources: Choreo's current swerve formulation, Sleipnir's current exit statuses and solver options, and the Choreo 2026.0.3 release notes.

Recommendation

Build Optimizer v2 as a path-parameterization engine, not a general-purpose nonlinear program:

  1. Keep the authored planar curve and heading law fixed.
  2. Parameterize them by translation arc length s.
  3. Use state x = ṡ² and control u = s̈, with discrete progress dynamics x[i+1] = x[i] + 2 Δs u[i].
  4. Project velocity, acceleration, deceleration, centripetal, angular, tank-wheel, and swerve-module constraints onto bounds in (u, x).
  5. Compute backward controllable intervals, then run a forward greedy pass choosing the greatest feasible progress speed. This is the TOPP-RA pattern and is roughly O(mN) for m inequalities and N grid points.
  6. Independently validate a denser reconstruction. If a midpoint violates a limit, adaptively insert grid points and resolve. Never report success from solver status alone.

For fixed geometry, several Bordeaux constraints are especially friendly to this formulation. Translation and angular acceleration are affine in (u, x): q̈ = q′u + q″x. A norm limit on an affine function of the scalar u becomes a quadratic interval that can be solved analytically, so Phase 1 does not need a generic QP/SOCP library. Swerve module speed is proportional to ṡ, so its squared norm gives a direct upper bound on x. Tank left/right wheel speeds and accelerations have the same property.

Product boundary. Optimizer v2 optimizes timing and respects authored geometry. A future geometry optimizer must be an explicit clone/preview/apply action, consistent with Bordeaux's rule against silent geometry mutations. It should never be hidden behind the existing optimizedTrajectory planner ID.

Result contract: eliminate the word “unsolvable”

StatusMeaningUser behavior
optimalReachability solution passed independent dense validation.Use and export normally; show solve time and active limiting constraints.
feasibleA safe profile passed validation but missed the optimality/refinement budget.Use it, label it “Feasible (not fully optimized),” and allow retry at higher quality.
invalid-inputA precise authored conflict exists: impossible boundary velocity, zero-length moving phase, stop/constraint contradiction, nonfinite geometry, etc.Point to the exact waypoint/range and proposed manual remedy. Do not retry blindly.
infeasibleThe backward reachable set becomes empty and the dense validator confirms the conflict.Report the first empty interval, active constraints, and nearest feasible boundary value.
cancelledA newer edit superseded the solve.Silent replacement; never toast as an error.
internal-errorInvariant, arithmetic, worker, or serialization failure.Keep the last valid trajectory; visibly fall back to profiledSpline; preserve diagnostics.

Implementation steps

  1. Phase 0 — freeze the contract and build the corpus (2–3 days). Add curated fixtures covering swerve/tank, every segment type, manual/targets/tangent/lookAt heading, reverse driving, all range anchors, short ranges between samples, authored interior stops, start/goal velocities, translation/heading priority, turns, waits, jiggles, self-overlaps, and degenerate/invalid cases. Add seeded fuzz generation. Capture current profiledSpline and optimizedTrajectory timing, output time, active limits, and diagnostics.
  2. Phase 0.5 — three bounded spikes (3–5 days total). Run the same corpus through: (a) current TrajoptLib/Sleipnir as a native CLI oracle, (b) TOPPRA C++ with one Bordeaux constraint adapter, and (c) a TypeScript reachability prototype for linear/arc/tangent-heading paths. Stop the comparison once one approach meets the gates below. Do not integrate UI or change project files during the spike.
  3. Phase 1 — canonical path-state model (3–4 days). Extract a typed, immutable sampled path boundary from the current planner: arc length, position, tangent, curvature, unwrapped heading, first/second derivatives, waypoint/sample mapping, effective ranges, stops, and priority policy. Keep geometry generation behavior unchanged. Add numeric differential fixtures for the static renderer mirror.
  4. Phase 2 — reachability solver (5–8 days). Implement velocity caps, forward/reverse acceleration bounds, controllable-interval propagation, forward time-optimal extraction, boundary velocities, authored stop sectioning, and deterministic active-constraint attribution. Start with existing aggregate robot hard limits; add exact tank wheel-speed projection and rectangular-swerve module-speed projection. Use tolerance and scaling constants in one module, not scattered magic numbers.
  5. Phase 3 — dense validator and adaptive grid (4–6 days). Reconstruct at midpoints and extrema; independently evaluate final velocity, acceleration, deceleration, curvature, angular velocity/acceleration, module/wheel speed, and every overlapping range. Refine only offending intervals. Put a strict sample/work ceiling before allocation. A candidate cannot be returned as optimal or feasible without this pass.
  6. Phase 4 — Bordeaux motion features (4–6 days). Preserve heading-priority slowdowns. For translation priority, parameterize translation first and pass timing to the existing bounded angular follower. Preserve the shared stationary postprocessor order arrival → turn → jiggle → wait → departure; do not optimize these phases twice. Remap markers by stable path fraction.
  7. Phase 5 — worker and preview integration (4–6 days). Keep the immediate synchronous profiledSpline preview while dragging, schedule optimized preview in a dedicated Web Worker with generation IDs and cancellation, then swap it in atomically. Use the same typed result contract in shared export/agent code. Route Java export through its existing worker and move any newly heavy analysis calls off Electron's main thread. Preserve only the two supported planner IDs.
  8. Phase 6 — mirrored renderer implementation (3–5 days). Mirror the numeric core in public/renderer only after the shared implementation is stable. Add randomized differential tests comparing position, heading, velocities, timestamps, stops, range attribution, status, and dense validation between the two boundaries.
  9. Phase 7 — shadow rollout (3–5 days plus soak). Behind a non-serialized developer flag, run v2 beside the current planner on the corpus and opt-in projects. Record only local aggregate timings/statuses unless telemetry is separately authorized. Promote v2 behind optimizedTrajectory when the gates pass; retain profiledSpline as a visible safety fallback for one release.
  10. Phase 8 — jerk and optional geometry refinement (separate projects). Treat nonzero translational jerk as a distinct third-order feature: either add a bounded jerk-smoothing pass that re-runs all checks, or explicitly reject it in Optimized until implemented. Explore Clarabel/OSQP sequential-convex geometry refinement only as an explicit cloned preview with Apply/Cancel.

Risks & mitigations

RiskLikelihoodMitigation
Path derivatives are noisy at segment boundariesmediumPreserve explicit stops/corners as phase boundaries; use analytic derivatives where available; unwrap heading before differentiation; adaptively refine and validate both sides of every boundary.
Aggregate drivetrain model is optimisticmediumPhase 1 is no weaker than today's hard-limit contract. Add exact wheel/module speed first, then a conservative combined translational/angular force envelope. Compare against TrajoptLib oracle before claiming drivetrain-time optimality.
Fixed geometry gives a slower path than Choreo can discoverhighThis is intentional product behavior. Offer explicit geometry refinement later and show predicted time improvement before Apply.
Reachability discretization misses a narrow range or peakmediumInsert every authored boundary into the grid; use interval overlap semantics; dense midpoint/extrema checks; recursively refine offending intervals.
Renderer/shared copies driftmediumOne fixture schema, seeded numeric differential tests, identical rounding/status contracts, and release verification budgets.
Jerk limits make the state second-orderhigh when enabledDo not pretend TOPP-RA's second-order result satisfies jerk. Gate nonzero jerk, add a separately validated smoother, or adopt a third-order reachability algorithm in a later plan.
Fallback hides a real defectmediumFallback only on internal-error; preserve v2 diagnostics and planner-used metadata; invalid/infeasible inputs never silently run another planner.

Verification

  • Focused unit tests for interval algebra, boundary scaling, swerve/tank projections, active-range overlap, stop sectioning, and every result status.
  • Property tests: monotonic s/t, finite samples, nonnegative speed, exact start/goal/stop velocities, tighter constraints never reduce trajectory time, and increased physical limits never increase optimal time.
  • Metamorphic tests: translation/rotation of the whole field, path reversal, uniform unit-safe scaling cases, path rename, duplicate, and serialization round trip.
  • Dense independent validation at 4× the solve grid plus analytic extrema where possible.
  • Cross-boundary randomized differential tests between src/shared and public/renderer.
  • Benchmarks on macOS arm64/x64 and Windows x64 with cold start, warm solve, edit-locality, cancellation, worst-case range count, and long path cases.
  • Before shipping: npm test, npm run typecheck, npm run build, env -u ELECTRON_RUN_AS_NODE npm run test:smoke, release packaging, and npm run verify:package against the packaged manifests.

Open questions

  • Should Optimized v2's first production contract be authored-geometry timing only (recommended), or must it be allowed to move the path?
  • Is a native solver acceptable if the spikes show a meaningful quality gain, or is the no-native TypeScript/browser boundary a firm product constraint?
  • Should nonzero translational jerk block Optimized v2 until a third-order method exists, or may the first release visibly return “Feasible, jerk smoothing applied”?
