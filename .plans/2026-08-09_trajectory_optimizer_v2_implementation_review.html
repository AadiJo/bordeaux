The first TypeScript reachability slice is fast, deterministic, explicitly classified, and safe enough to continue—but it is deliberately labeled feasible, not optimal, until dense drivetrain validation exists.

Context

This review covers the first implementation slice of Trajectory optimizer strategy for Bordeaux on branch feat/trajectory-optimizer-v2. The goal was to replace heuristic neighbor smoothing with a small fixed-geometry reachability core while preserving authored geometry, stops, constraint ranges, markers, and the two supported planner IDs.

The implementation is separated into a generic numeric core, a Bordeaux constraint adapter, and thin planner orchestration. That boundary keeps a future standalone extraction practical without introducing a package or native runtime prematurely.

Recommendation

Continue with the custom TypeScript route. This spike meets the early latency, determinism, packaging, and classified-outcome goals without Sleipnir's nonlinear convergence behavior or a native dependency. Do not claim time optimality yet: the adapter conservatively inherits the current profiled-spline geometry/rotation envelope, and the validator currently covers final linear limits rather than dense drivetrain reconstruction.

Review result: no blocking issue remains in this slice. Two issues found during review were fixed before publication: partial-range boundary caps now constrain both interval endpoints, and under-resolved stopped intervals can no longer produce enormous nominal durations. A post-solve validator failure now visibly falls back with internal-error.

Implemented

  • reachability.ts: deterministic backward controllable-envelope and forward maximum-feasible extraction with torque-speed taper, authored boundary velocities, interior stops, input validation, and explicit optimal/invalid-input/infeasible core outcomes.
  • optimizationConstraints.ts: isolated translation of Bordeaux global/range constraints and the existing geometry/rotation envelope into solver inputs, plus independent final linear validation.
  • optimizedTrajectory.ts: removed iterative smoothing, remapped time and markers from the solved speeds, added result status/iteration diagnostics, preserved visible profiled-spline fallback only for internal failures, and returned authored conflicts as blocking classified diagnostics.
  • Regression tests cover trapezoidal reachability, stops, torque-speed taper, malformed and infeasible inputs, deterministic planner output, all range anchors, partial-range boundaries, invalid short start/stop paths, and under-resolved grids.
  • npm run benchmark:planners adds repeatable demo, curved, and range-plus-stop measurements with status and violation gates.
