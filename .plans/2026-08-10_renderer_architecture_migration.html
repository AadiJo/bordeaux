Move the existing React renderer from hand-ordered global scripts to Vite-built React + TypeScript modules, keep SVG for the field, and consolidate renderer math into the typed shared domain before considering Canvas or WebGL.

Implementation progress

Stage 1 is complete. The production app now loads a Vite-built renderer from dist-renderer. React and ReactDOM are build-time npm dependencies, the CSP-protected HTML has one module entry, renderer globals are isolated in a typed compatibility bootstrap, and the existing UI/SVG implementation has moved under src/renderer/legacy for incremental conversion.

Context

The renderer is not pure HTML/CSS today. It ships React 18.3.1, but uses production UMD files, window.* globals, IIFEs, and thousands of manual React.createElement calls. The HTML is only a root element plus sixteen ordered script tags.

String-based testsSeveral tests prove behavior by searching source text rather than importing typed functions or exercising the rendered UI.

Recent work already made sensible runtime optimizations: pointer motion is coalesced with requestAnimationFrame, playback uses an external store below the root, path derivation is memoized, and static SVG layers are memoized. Those changes mean a renderer rewrite should begin with architecture and measurement, not an assumption that React or SVG is inherently slow.

Recommendation

Adopt Vite + React + TypeScript, preserve the Electron security model and SVG field, and migrate through a compatibility entry point. This improves maintainability immediately and creates the module boundaries needed for targeted performance work. TypeScript and TSX do not make runtime rendering faster by themselves; production bundling, code splitting, shared-domain reuse, and smaller render subscriptions are the actual performance levers.

Do not start with Canvas/WebGL. SVG currently provides DOM event targets, transforms, hit testing, and inspectable geometry. A Canvas rewrite would recreate those systems and increase migration risk. Only revisit it after a trace shows SVG reconciliation or node count—not path derivation or root state fan-out—is missing the frame budget.

Implementation steps

  1. Record the baseline. Capture renderer build bytes, startup timing, and a representative waypoint-drag trace before changing architecture. Use a medium project and record path derivation time, scripting time, dropped frames, and SVG node count.
  2. Add a production renderer build. Add React/ReactDOM, Vite, the React plugin, and React types as build-time dependencies. Use base: "./" so output works under Electron’s file:// loading. Emit to dist-renderer.
  3. Preserve behavior through a compatibility bootstrap. Start with one module entry that provides the temporary globals and loads the existing renderer files in their current order. Update BrowserWindow.loadFile, package inclusion, CSP verification, and the eager-byte budget to point at built output. This makes the build reversible before component conversion begins.
  4. Convert domain code before UI code. Make src/shared/math/pm.ts the canonical path-math module by porting renderer-only helpers with focused unit tests. Import it from both planner/export and renderer paths. Convert unit preferences, path links, pointer drag, and routine modeling into typed modules next.
  5. Convert components one boundary at a time. Move primitives, panels, inspectors, field view, and finally the app shell into .tsx. Replace window.* with direct imports and typed props. Keep markup, CSS class names, Electron IPC, and visible behavior unchanged during this pass.
  6. Break up the app controller after parity. Extract project/history, Java integration, agent proposal handling, and playback into focused hooks or reducers. Do not add Redux/Zustand unless a concrete cross-feature subscription problem remains. Split CSS by feature for ownership while allowing Vite to emit consolidated production CSS.
  7. Optimize only measured hot paths. If path derivation blocks dragging, move it to a worker or use a cheaper transient preview while dragging and commit full derivation on the next frame/pointer release. If React fan-out dominates, subscribe field/inspector regions to narrower state. Consider Canvas only if the trace isolates SVG node reconciliation as the bottleneck.

Risks & mitigations

RiskLikelihoodMitigation
Behavior changes hidden inside a broad rewritemediumSeparate build adoption, domain consolidation, TSX conversion, and state refactoring into behavior-preserving commits.
Vite output fails under file:// or CSPlowUse relative asset paths, no inline scripts/styles, keep context isolation/sandboxing, and run the packaged Electron smoke test.
Renderer and shared math differ during consolidationmediumAdd fixture-based parity tests before deleting the browser copy; treat current renderer behavior as an explicit compatibility input, not automatically correct.
Bundle pipeline increases release sizelowKeep an output-byte budget, exclude source maps and renderer source from packages, and inspect the packaged ASAR.
Migration stalls with two architecturesmediumTrack file-by-file ownership, forbid new code in legacy globals after bootstrap lands, and delete each compatibility global as its module is converted.

Verification

  • npm run typecheck includes renderer source and Electron source.
  • npm test replaces source-string assertions with imported domain tests and focused renderer behavior checks where practical.
  • npm run build builds the renderer before Electron and verifies local-only resources, production React, CSP, and an explicit JS/CSS budget.
  • env -u ELECTRON_RUN_AS_NODE npm run test:smoke verifies packaged-style loading, IPC, accessible control names, path editing, and save behavior.
  • Compare the same performance trace before and after. The migration must not regress waypoint dragging or playback; bundle/startup improvement should be reported from measurements rather than assumed.

Open questions

  • No architectural choice blocks the first stage. The Canvas/WebGL decision is intentionally deferred until profiling provides evidence.
  • Hot-module reload can be added after the production build is stable; it should not complicate the first migration commit.
